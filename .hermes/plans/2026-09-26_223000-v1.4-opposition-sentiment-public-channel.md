# v1.4 — Opposition, Sentiment and the Public Channel: Implementation Plan

> **For Hermes:** reconnaissance is DONE (all endpoints probed live 2026-09-25/26). This plan is
> only the build. Every endpoint below returned HTTP 200 with a real measured value; every dead
> end is recorded with its status code.

**Goal:** Move the model's blind spot from *"sentiment and politics are unmeasurable"* to
*"three of the four channels are measured, and the one that matters most is measured with a
stated direction."*

**Architecture:** two new source modules (`gdelt.rs`, `courtlistener.rs`), one new indicator
(`opposition_pressure`), one extension to an existing indicator (`narrative_saturation` gains a
news-tone leg), and one new falsifier. The hard-data leg (court filings) carries the scored
weight; the sentiment leg is measured, reported, and **explicitly not scored** until it is
proven to lead rather than lag.

**Tech Stack:** Rust, existing `Fetcher` (per-host circuit breaker, no TTL), `chrono`,
existing `IndicatorCfg` + anchors pattern, existing falsifier panel.

## The design decision that makes this different from financial astrology

Daim has zero tolerance for pattern-matching dressed as prediction, so the ordering here is
deliberate and is the whole point of the plan:

**1. Court filings are HARD data.** A filed lawsuit or adopted moratorium is a recorded event
with a docket number. It is not an opinion, it cannot be astroturfed, and it is the mechanism by
which opposition actually *reduces* future revenue. This leg carries the scored weight.

**2. News coverage is the TRANSMISSION channel.** It is not itself causal, but it is upstream of
politics and politics is upstream of permits.

**3. "AI bubble" tone is deliberately NOT scored.** Measured this session, it hit the 1.2th
percentile — but we do **not** yet know whether attention/tone **leads** a repricing or **follows**
it. A series that spikes *after* a drawdown is a lagging indicator that would be actively
harmful to score. Task 7 resolves this with a lead/lag correlation against the archive before it
is ever given weight. **Until then it is reported as context, like `trend`.**

**4. The direction of a HIGH reading is genuinely ambiguous and must be stated.** `datacenter_construction`
measures what is built; `grid_cancellations` measures what was cancelled. Opposition *pressure*
is the third thing — and the honest reading is two-sided: rising opposition is **bubble-consistent**
(a real constraint arriving) but **also counter-evidence** (it implies the buildout is financially
durable enough to be worth fighting, rather than quietly abandoned). The existing
`energisation_delay` rationale already models this "both are true and neither is asserted"
pattern; follow it exactly.

## Task 1 — `src/sources/gdelt.rs`: the GDELT source

**Objective:** fetch a daily volume series and a daily tone series for named queries.

**Files:**
- Create: `src/sources/gdelt.rs`
- Modify: `src/sources/mod.rs` (module decl + `fetch_all` wiring)
- Test: inline `#[cfg(test)] mod tests` in `gdelt.rs`

**Hard constraints learned live — all three cost a real failure:**

1. **One request per 5 seconds, enforced.** Two concurrent calls returned **HTTP 429** with
   `Please limit requests to one every 5 seconds`. Two calls 7s apart *also* 429'd on the second.
   Treat this as a **serialised** host: one in-flight request at a time, **≥6s** apart, retry once
   on 429 with a 10s backoff, then degrade to a gap. Never parallelise this host.
2. **Query syntax: no bare parentheses.** `(a OR b) AND c` returns
   `Parentheses may only be used around OR'd statements.` Use `a+OR+b` or plain multi-term.
3. **`format=json` returns `{timeline:[{data:[{date,value}]}]}`.** The `date` field is
   `YYYYMMDDTHHMMSSZ`; slice `[..8]`. Tone is `timelinetone` (negative = hostile), volume is
   `timelinevol` (a **fraction of all coverage**, not an absolute count).

**Step 1: write the failing test — series parsing**

```rust
#[test]
fn a_tone_series_parses_its_actual_nested_shape() {
    let body = r#"{"timeline":[{"data":[
      {"date":"20260920T000000Z","value":-0.5},
      {"date":"20260921T000000Z","value":-3.48}
    ]}]}"#;
    let s = parse_timeline(body).unwrap();
    assert_eq!(s.len(), 2);
    assert_eq!(s[1].date, "2026-09-21");
    assert!((s[1].value - (-3.48)).abs() < 1e-9);
}
```

**Step 2: run it, watch it fail** — `cargo test --release --lib sources::gdelt`, expect
`cannot find function parse_timeline`.

**Step 3: the 429 body must be an ERROR, not an empty series.** This is the failure mode that
matters: a rate-limit reply body is *not* JSON, and a permissive parser returns an empty series,
which then reads as "no opposition coverage" — i.e. a **calm** signal produced by a *refusal*.

```rust
#[test]
fn a_rate_limit_body_is_an_error_not_an_empty_series() {
    // The live 429 body begins "Please limit requests to one every 5 seconds"
    let body = "Please limit requests to one every 5 seconds or contact ...";
    assert!(parse_timeline(body).is_err(), "a refusal must never parse as a calm reading");
    assert!(parse_timeline("").is_err());
    assert!(parse_timeline("{}").is_err(), "no timeline key is not an empty timeline");
}
```

**Step 4: implement `parse_timeline` + `fetch_timeline`.** Serialise on the host with a
`Fetcher`-level guard, or simply accept the latency: this source makes **3 requests** (tone,
resistance volume, moratorium volume), so a **18s** minimum wall clock. Budget it against the
900s systemd cap (current run is ~371s, so this is comfortable).

**Step 5: verify against the live endpoints** (measured values above).

**Step 6: commit** — `feat: GDELT source for news volume and tone (serialised, 429-aware)`

## Task 2 — `src/sources/courtlistener.rs`: the hard-data source

**Objective:** date-bounded docket counts for opposition queries.

**Files:** Create `src/sources/courtlistener.rs`; modify `src/sources/mod.rs`.

**Step 1: failing test — count parsing**

```rust
#[test]
fn a_docket_search_yields_its_count_and_says_when_it_cannot() {
    assert_eq!(parse_count(r#"{"count":331,"results":[]}"#).unwrap(), 331);
    // A body without `count` is a failure, not a zero.
    assert!(parse_count("{}").is_err());
    assert!(parse_count("<html>403</html>").is_err());
}
```

**Step 2: implement.** Endpoint measured working:
`https://www.courtlistener.com/api/rest/v4/search/?q=%22data+center%22+moratorium&filed_after=2025-01-01&filed_before=2026-09-26&type=r`
→ `{"count":33,...}`. No key, no exposed rate-limit headers; still throttle to ~1/2s.

**Step 3: define the queries and record each separately**, never summed into one number:
- `"data center" moratorium`
- `"data center" lawsuit`
- `"data center" injunction`

**Step 4: critical — a count is not a series, so score it against its own history.** The count is
comparable across equal-length windows only. Use two fixed 365-day windows (trailing year vs the
year before) and score the **year-over-year change**, mirroring `narrative_saturation`. Do **not**
score the level: the corpus grows every year, so a rising raw count is expected and meaningless.

**Step 5: commit** — `feat: CourtListener source for docket counts (hard opposition data)`

## Task 7 — the lead/lag test (THE GATE — do this before scoring any sentiment)

**Objective:** determine empirically whether sentiment/attention **leads** or **follows** price.

**Files:** create `.hermes/analysis/2026-09-26-sentiment-lead-lag.md`; a throwaway script.

**Method:** correlate the tone series and the attention series against the archive's composite and
against an equity series already fetched, at lags of −10…+10 days. Report the peak correlation and
its lag. Record the result **even if it is null** — a null result is the finding that stops this
project from shipping financial astrology.

**Decision rule, stated in advance:**
- tone/attention **leads** price at a peak with |r| meaningfully above the noise floor → eligible
  for scoring, with the lead length recorded in the rationale.
- tone/attention **follows** or shows no peak → stays unscored context **permanently**, and this
  document is the reason.

**Commit** — `docs: the lead/lag finding — why tone is (or is not) scored`

## Risks and tradeoffs

1. **GDELT's 5s rate limit makes it slow and serial.** Three queries ≈ 18s minimum. Acceptable
   now; if it grows, cache with a TTL (which this project currently lacks).
2. **GDELT `timelinevol` is a fraction of all coverage, not a count.** A 6.33x rise is *share*
   growth. If total news volume also grew, the true increase is smaller. **Must be stated in the
   rationale** — this is exactly the "a share ratio is not a level" trap already documented.
3. **CourtListener is a US-court corpus.** Local zoning — where most resistance occurs — is
   absent. Lower bound, stated.
4. **The tone series may be a lagging indicator.** That is the single largest risk to the project's
   credibility, and Task 7 exists purely to settle it before anything is scored.
5. **Two more network sources on a Pi** with an existing 15.5 MB/day already in the budget.
   GDELT and CourtListener are small JSON, but the run time grows ~20-30s.

## On the Oracle claim specifically

Daim's read of the news is already **partly measured** rather than needing a new indicator: the
model has Oracle-specific findings in **three** places, all live today.

- **`leverage`** — `us-gaap:LongTermDebt` resolved for ORCL to a stale 2022-05-31 fact worth
  exactly zero, so the old resolver reported *the most leveraged company in the cohort as carrying
  no debt*. Fixed: its notes are ~**$122bn** under `us-gaap:LongTermNotesPayable`; cohort mean moved
  0.556x → 0.955x operating cash flow, an understatement of **15.1 stress points**.
- **`backlog_quality`** — ORCL RPO **137.8B → 455.3B in ONE quarter (+230%)** while deferred revenue
  went 10.7B → 13.4B, taking its ratio **12.8x → 49.4x**. GOOGL 51.4x, MSFT 9.0–11.8x. The
  *divergence from billed cash* is the signal — i.e. the model already encodes “Oracle is booking
  enormous commitments that are not converting to cash.”
- **`depreciation_subsidy`** — ORCL's depreciation rate fell **6.41% → 6.22%** while gross PP&E grew
  **4.28x**, the single flagged anomaly of nine companies.

So the *financial* overstretch reading is covered. What is **not** covered is the *opposition*
channel — which is precisely what Tasks 1–3 add. No new Oracle-specific work is needed.

## A note on sequencing

This plan deliberately front-loads the **unsexy** task: Task 7 (the lead/lag test) gates every
scored sentiment decision. If it comes back null, Tasks 4 and 6 ship as documented context and the
project keeps its empirical footing. That ordering is the answer to “how do we track this daily
without it becoming astrology” — not a new data source, but a test that can *disqualify* the
data source.
